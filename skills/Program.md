# Program.md

旨在减少 LLM 常见编码错误的行动准则。请根据需要与项目特定说明结合使用。

**权衡：** 这些准则在速度与谨慎之间更倾向于谨慎。对于简单任务，请自行判断。

## 1. 编码前先思考

**切勿臆断。切勿掩饰困惑。明确权衡利弊。**

在实施之前：
- 明确陈述你的假设。如果不确定，请提问。
- 如果存在多种解读方式，请将其列出——不要默默自行选择。
- 如果有更简单的方案，请提出来。必要时提出异议。
- 如果某处不清楚，请停下来。指出困惑之处并提问。

## 2. 简洁至上

**用最少的代码解决问题。不做任何预判性开发。**

- 不添加超出需求的功能。
- 不为仅使用一次的代码进行抽象。
- 不添加未被要求的“灵活性”或“可配置性”。
- 不针对不可能发生的场景编写错误处理逻辑。
- 如果写了 200 行代码但其实 50 行就能搞定，请重写。

问问自己：“资深工程师会认为这太复杂了吗？”如果是，请简化。

## 3. 精准修改

**只改动必要部分。只清理自己造成的混乱。**

修改现有代码时：
- 不要“顺手改进”相邻的代码、注释或格式。
- 不要重构没有问题的代码。
- 遵循现有风格，即使你习惯用不同的方式编写。
- 如果发现无关的死代码（dead code），请指出——不要直接删除。

当你的修改导致代码冗余（孤立代码）时：
- 移除因你的修改而不再使用的导入（import）、变量或函数。
- 除非有要求，否则不要移除原有的死代码。

检验标准：每一行修改都应能直接追溯到用户的需求。

## 4. 目标导向执行

**明确成功标准。** **循环迭代，直至验证通过。**

将任务转化为可验证的目标：
- “添加验证” → “针对无效输入编写测试，并确保测试通过”
- “修复 Bug” → “编写测试以复现该 Bug，并确保测试通过”
- “重构 X” → “确保重构前后的测试均能通过”

对于多步骤任务，请简要说明计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

明确的成功标准能让你独立进行迭代；而模糊的标准（如“让它能跑通”）则需要不断沟通确认。

---

**若出现以下情况，说明这些准则行之有效：** 代码变更（diff）中不必要的改动减少了；因过度复杂化而导致的重写减少了；且澄清问题的沟通发生在实施之前，而非在出错之后。
